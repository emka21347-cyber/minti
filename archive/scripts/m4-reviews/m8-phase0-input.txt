You are reviewing the protocol spec + implementation plan for MINTI M8 — a
NEW Clan-joining flow ("knock by clan-id"). MINTI's Clan layer currently has
two joining flows (§3.2 invite-token, §3.3 BIP39 paste-key), both of which
require the joiner to receive out-of-band auth material BEFORE joining. M8
adds a third path where the joiner only needs the Clan ID + a reachable LAN
address; the existing-Clan operator visually verifies a 6-digit SAS code with
the joiner over a side channel (phone, in-person, Signal) before accepting.

The crypto core: ephemeral X25519 ECDH between joiner and receiver, with the
shared secret fed through HKDF-SHA256 binding BOTH pubkeys + clan_id +
knock_id into the info. The output is split into (32-byte AES-256 key,
4 bytes of SAS material, 12-byte AES-GCM nonce). Receiver seals a
WelcomeResponse with AES-256-GCM keyed by the HKDF output and aad=knock_id;
joiner opens with the same key/nonce/aad. The GCM tag is the receiver-
authenticity proof.

Your job is to find concrete problems, not to be polite. Be willing to say
"looks good" rather than padding criticism. Be willing to disagree with the
plan author. Cite spec sections (e.g. "§3.4 confirm-code semantics") or
plan sections (e.g. "Rate limits") by name so the author can find them.

Look for, in this priority order:

1. **Cryptographic correctness.** Is the HKDF construction sound (salt
   namespacing, info binding, output split)? Is reusing a deterministic
   nonce safe given that each (joiner_pub, receiver_pub) pair derives a
   distinct key? Does the SAS derivation leak information about the key?
   Is the GCM aad=knock_id binding sufficient, or should the aad also
   include clan_id / pubkeys?

   weakness. The joiner exposes an anonymous endpoint waiting for a sealed

3. **Active MITM on /clan/knock.** TLS-with-SPKI-pin protects §3.2/§3.3

## 3. Membership

### 3.1 States

```
unaffiliated --(create)--> active (founder)
unaffiliated --(invite + admit)--> admitted --(handshake)--> active
admitted --(timeout 24h)--> unaffiliated
active --(revoke)--> revoked --(48h grace)--> purged
active --(self-leave)--> unaffiliated
```

### 3.2 Invite flow (preferred)

1. An `active` member with sufficient authority (v1: any active member) calls `POST /clan/invite` with `{"ttl_seconds": <60..86400>, "as_role": "auto"}`.
2. Server returns:
   ```json
   {
     "token": "<base64url 32 bytes>",
     "clan_id": "...", "clan_cert_pin": "sha256:...",
     "lan_address": "192.168.1.42:7777",
     "expires_at": "2026-05-21T18:30:00Z"
   }
   ```
3. The candidate (running `cland --join <token>`) calls `POST /clan/join` on the issuer with `{"token": "...", "member_id": "...", "member_pubkey": "..."}`.
4. Issuer verifies token, then returns `clan_key` (and `clan_cert` for pinning). Token is consumed (single use).
5. Candidate persists `clan_id`, `clan_key`, pinned `clan_cert`, and transitions to `admitted`, then `active` on first successful capability advertisement.

### 3.3 Paste-key flow (fallback)

For low-friction joining without out-of-band token exchange:

1. An existing member exposes the Clan Key via one of:
   - **QR code** encoding the full 256-bit `clan_key` directly, OR
   - **12-word BIP39 mnemonic** encoding a 128-bit derivation seed.
2. Candidate enters the phrase (or scans the QR), plus the LAN address of any active member.
3. Candidate connects, advertises identity, and is admitted on the active member's policy.

**Entropy and key derivation.** When the mnemonic path is used, the candidate's `cland` expands the 128-bit BIP39 seed to the full 256-bit `clan_key` via `HKDF-SHA256(seed, salt="minti-clan-key", info="v1")`. The 128-bit seed is sufficient for v1's trusted-LAN threat model — brute-forcing 128 bits is infeasible with current hardware. The QR path uses the full 256 bits directly. v2 mTLS replaces the shared `clan_key` entirely and closes the 128-bit gap.

**Trust caveat:** any sniffer in the QR/voice channel sees the Clan Key. Use only over trusted channels (sitting at the same desk, secure messenger).

### 3.4 Knock flow (live in-person / Signal-call onboarding)

For onboarding a new node when the joiner has *no out-of-band secret* — only knowledge of the Clan ID and a reachable LAN address of an active member. Trust is established by an **ephemeral X25519 ECDH** between joiner and receiver plus a **20-bit Short Authentication String (SAS)** — a 6-digit numeric confirm-code — that the existing-Clan operator visually verifies with the joiner over a side channel (phone call, in-person, Signal). Modelled on the Signal pairing flow.

This flow coexists with §3.2 (invite-token) and §3.3 (paste-key). Choose by handoff style:

| Flow | Joiner needs… | Best for |
|---|---|---|
| §3.2 Invite-token | Token + LAN address + cert pin (single line) | Asynchronous remote ("paste this in the SSH session you opened on the new box") |
| §3.3 Paste-key | 12-word BIP39 mnemonic | Trusted-channel one-shot ("here's the phrase, save it somewhere safe") |
| §3.4 Knock | Clan ID + any active LAN address | Live in-person or Signal-call onboarding ("you're sitting next to me — let's join your laptop now") |

**Wire endpoints.** Two on the **receiver** side (any active Clan member can act as receiver), one on the **joiner** side:

| Endpoint | Side | Auth | Purpose |
|---|---|---|---|
| `POST /clan/knock` | Receiver | Anonymous (joiner has no `clan_key` yet) | Initiate the knock; receiver stores it pending operator decision |
| `GET /clan/knock-list` | Receiver | HMAC (Clan member operator) | TUI / CLI reads pending knocks for display |
| `POST /clan/knock-accept` | Receiver | HMAC | Operator accept; triggers encrypted delivery to joiner |
| `POST /clan/knock-deny` | Receiver | HMAC | Operator deny; receiver pings joiner with reason |
| `POST /clan/knock-deliver` | Joiner | **AES-GCM tag is the auth** (no HMAC; joiner doesn't have `clan_key` yet) | Receiver delivers the sealed welcome blob; joiner opens, persists, becomes `active` |

**Request / response shapes.**

```json
// → POST /clan/knock  (anonymous)
{
  "clan_id":                  "<UUIDv4>",
  "joiner_member_id":         "<UUIDv4>",
  "joiner_identity_pub_b64":  "<base64 Ed25519 pubkey>",
  "joiner_x25519_pub_b64":    "<base64 ephemeral X25519 pubkey>",
  "joiner_display":           "alice-macbook",
  "joiner_addr":              "192.168.56.103:7777"
}

// ← KnockResponse
{
  "knock_id":                 "<hex 16 bytes>",
  "receiver_x25519_pub_b64":  "<base64 receiver's ephemeral X25519 pubkey>",
  "confirm_code":             "541-829",
  "ttl_seconds":              300
}
```

**Cryptographic core.** Both sides derive the *same* `(key, nonce, confirm_code)` from the same inputs. The receiver computes them when it stores the pending knock; the joiner computes them once it has the `KnockResponse`.

```
shared    = X25519(my_x25519_priv, peer_x25519_pub)            // 32 bytes
salt      = "minti-knock-v1"
info      = clan_id || knock_id || joiner_x25519_pub || receiver_x25519_pub
kdf       = HKDF-SHA256(IKM=shared, salt=salt, info=info)
read 48 bytes from kdf into bundle:
  key           = bundle[0:32]                                  // AES-256 key
  code_bytes    = bundle[32:36]                                 // SAS
  nonce         = bundle[36:48]                                 // 12-byte GCM nonce
confirm_code    = sprintf("%03d-%03d",
                          BE_uint32(code_bytes) / 1_000 mod 1_000,
                          BE_uint32(code_bytes)         mod 1_000)
```

The static salt is namespaced (`"minti-knock-v1"`) so future protocol versions can rotate it. **`clan_id` and `knock_id` are in `info`** — without them, an attacker could precompute `(joiner_pub, receiver_pub) → confirm_code` tables offline; with them, every knock window requires a fresh derivation. The nonce is deterministic but safe: each `(joiner_pub, receiver_pub)` pair derives a unique `key`, so the same nonce never re-encrypts under the same key.

**Sealed welcome.** When the operator accepts, the receiver builds the same `WelcomeResponse` payload it would for §3.3 (clan_id, clan_cert_pem, clan_cert_priv_key_b64, clan_key_b64, roster) and seals it:

```
plaintext  = json.encode(WelcomeResponse)
ciphertext = AES-256-GCM_seal(key, nonce, plaintext, aad=knock_id)
```

```json
// → POST /clan/knock-deliver  (on the joiner's listener)
{
  "knock_id":            "<hex 16 bytes>",
  "encrypted_blob_b64":  "<base64 ciphertext + GCM tag>"
}
```

The joiner looks up `knock_id` in its own pending-knock store (which remembers its ephemeral X25519 private key), derives the same `(key, nonce)`, and `AES-256-GCM_open(…, aad=knock_id)`. **The GCM tag is the receiver-authenticity proof** — only a party that knows `shared` (i.e. holds `receiver_x25519_priv`) can forge a valid tag. No separate signature is required.

**Confirm-code semantics.** 20 bits of SAS is borderline (Signal uses 60) but acceptable for this flow because: (a) the SAS is only valid for the knock TTL (default 300 s); (b) verification is human-eyeball over a side channel — the operator and joiner read the digits to each other and confirm match before accepting; (c) the LAN-bounded threat model limits an attacker's collision rate to network round-trip speeds. Brute-forcing the SAS during a single knock window requires ≈500,000 MITM attempts on average — orders of magnitude above what's stealthy. If an attacker substitutes pubkeys in transit, the SAS the joiner derives differs from the SAS the receiver displays; the operator catches the mismatch when reading codes with the joiner.

**State machine.**

```
joiner-side                                 receiver-side
-----------                                 -------------
(holds clan_id only)
generate ephemeral X25519
POST /clan/knock  ----------------------->  validate clan_id matches
                                            generate receiver X25519
                                            knock_id = rand(16 bytes)
                                            store PendingKnock{TTL=300s}
                <-----------------------    return KnockResponse
derive (key, nonce, code)                   derive (key, nonce, code)
display "Show this code: 541-829"
listen on joiner_addr for delivery          [operator opens TUI]
                                            shows pending knock + code
                                            [operator visually verifies
                                             "541-829" with joiner]
                                            [operator presses `a` accept]
                                            seal welcome with (key,nonce)
                <----------------------     POST /clan/knock-deliver
open + verify GCM tag
write clan.json, identity.json
transition to admitted
                                            promote roster entry to active
                                            on first /clan/advertise (§4.2)
```

**Acceptance authority.** *Any* member whose roster `state` is `active` (§3.1) may accept or deny incoming knocks. The Clan is peer-equal post-Phase H-1; centralisation through the elected Orchestrator is not required for membership decisions. First-write-wins: the joiner's KnockStore deletes the entry under lock on first successful `knock-deliver`; concurrent accepts from multiple members race for the CAS and the losers receive 409.

**Rate limits.** All values v1; tune per operational data later.

| Side | Bucket | Limit |
|---|---|---|
| Receiver | per `joiner_addr` (the IP:port in `/clan/knock`) | 10 / 60 s |
| Receiver | per `clan_id` (all knocks targeting one Clan) | 30 / 60 s |
| Joiner   | per `knock_id` on `/clan/knock-deliver` | 1 accept; further attempts 409 |
| Joiner   | per source IP for unknown `knock_id`s | 5 / 60 s |

The per-`clan_id` bucket prevents a swarm DoS against the receiver; the joiner-side IP bucket frustrates an attacker who scraped `/clan/knock` and tries to pre-seed delivery before the legitimate accept arrives.

**Threat model.**

| Attacker capability | Defence | Limit |
|---|---|---|
| Passive eavesdrop | TLS + SPKI pin on the knock leg (receiver advertises its existing Clan cert); ECDH ephemeral keys → forward secrecy | Standard |
| Active MITM swapping pubkeys | Confirm code binds *both* pubkeys + `clan_id` + `knock_id`; operator visually verifies digits | ≈1/2²⁰ collision per knock-window — observable |
| Replay old `knock-deliver` | `knock_id` is single-use via CAS on joiner | After consume, 409 |
| Cross-Clan replay | `clan_id` in HKDF info → different keys → GCM tag fails | Cryptographic barrier |
| Spam knocks (DoS) | Per-`joiner_addr` + per-`clan_id` rate limits | See table |
| Compromised existing member | Out of scope for §3.4; addressed by revocation (§3.5) | v1 honesty |

**TTL bounds.** Default knock TTL is 5 min (300 s). Min: 60 s. Max: 15 min (900 s). The joiner-side ephemeral private key is held only while the knock is pending; on expiry the joiner discards it. The receiver-side KnockStore sweeper runs every 60 s (same cadence as the InviteStore sweep) and evicts expired knocks.

**Identity persistence.** The joiner uses their pre-existing Ed25519 identity (from `identity.json`, the same one used for §3.2/§3.3 joining). A joiner with a previously revoked identity will appear to the operator with that identity's fingerprint — `JoinerIdentityFingerprint` is the first 8 hex chars of `sha256(joiner_identity_pub)` and is shown in the receiver's TUI. The operator decides whether to accept; the protocol does not auto-block previously revoked identities (operator may have explicit reason to re-admit).

# M8: Knock-by-Clan-ID Clan-joining flow

## Context

The existing Clan-joining flows (Phase C-rest) both require the joiner
to receive out-of-band auth material *before* joining:

1. **Invite-token**: founder pastes `minti-cland join --token X --address Y --pin Z`.
2. **BIP39 mnemonic**: founder shares the 12-word phrase from `create` once.

In the M7.x session, on seeing M7.6's TUI-mints-invite feature land, the
user asked: *"can the joiner just knock with the Clan ID, and have an
existing operator approve it in the TUI?"* — like Signal pairing or a
firewall knock pattern. The Clan ID is essentially public (mDNS-visible);
the trust comes from the operator visually verifying the joiner over a
side channel (phone, in-person, Signal) before pressing accept.

**Outcome**: a third joining flow that coexists with the two existing
ones. Knock for live in-person/Signal-call joining; mnemonic for
trusted-channel async handoff; invite-token for asynchronous remote
("paste this in the SSH session you opened on the new box"). Each
addresses a different threat / convenience point.

User-confirmed scope:
- **Any active Clan member can accept** (matches peer-equal trust model
  post-Phase H-1; first-accept-wins CAS prevents races).
- **Run the 3-LLM peer-review pass on this design BEFORE writing
  protocol code** (matches the M4-E/G/H/J + M5 convention; crypto-
  touching changes always get adversarial review first).

## Recommendation block

| Decision | Choice | Why |
|---|---|---|
| **Trust bootstrap** | Ephemeral X25519 ECDH + 6-digit human-verified SAS | Standard pattern (Signal-pairing-light). Defeats MITM as long as operator visually verifies the digits with the joiner over a side channel. Both `golang.org/x/crypto/curve25519` and `hkdf` already vendored in `cland/go.mod`. |
| **Symmetric cipher** | AES-256-GCM with deterministic nonce + `aad=knock_id` | GCM tag = receiver-authenticity proof; only the holder of the shared secret can forge it. Same primitive family Go stdlib already uses; no new deps. |
| **HKDF binding** | `info = clan_id ‖ knock_id ‖ joiner_x25519_pub ‖ receiver_x25519_pub` | Critical: per the Plan-agent review, omitting `clan_id`+`knock_id` from `info` lets an attacker precompute pubkey-pair-to-6-digit tables offline. Binding eliminates that. |
| **Confirm code** | 20-bit numeric SAS rendered "ABC-DEF" | Borderline (Signal uses 60); acceptable for LAN-bounded, TTL-bounded, human-verified flow. Threat model documented inline. |
| **Acceptors** | Any *active* Clan member | User's choice. Member's `state="active"` (from `state.RosterMember`) is the gate; admitted/revoked can't accept. First-write-wins CAS on the joiner's `KnockStore`. |
| **Discovery** | Paste-the-address for v1; mDNS in v1.5 | The existing `cland/internal/discovery/` package (grandcat/zeroconf) is reusable but v1's "paste `minti-cland knock --clan-id X --address Y`" matches the existing CLI ergonomics. |
| **Peer review** | 3-LLM pass via `scripts/m8-peer-review.py` before any code | Driver mirrors the existing `m4-phaseE-review.py` and similar; reviews land at `scripts/m4-reviews/m8-phase0-{deepseek-r1,gemma4,qwen3.6}.md`. Process: write protocol spec → run reviewers → triage findings → fold consensus blockers → only then write Go. |
| **Code organisation** | New files under `cland/internal/membership/` (not a new package) | Matches the existing `membership/invite.go`, `membership/handlers.go` shape. KnockStore reuses InviteStore's TTL+sweep pattern. |

## Protocol surface

### Wire shapes — `cland/internal/membership/knock.go` (new)

```go
// POST /clan/knock  — anonymous (joiner has no clan_key yet).
type KnockRequest struct {
    ClanID            string `json:"clan_id"`              // must match receiver
    JoinerMemberID    string `json:"joiner_member_id"`     // UUID
    JoinerIdentityPub string `json:"joiner_identity_pub_b64"` // Ed25519
    JoinerX25519Pub   string `json:"joiner_x25519_pub_b64"`   // ephemeral
    JoinerDisplay     string `json:"joiner_display"`       // hostname/label
    JoinerAddr        string `json:"joiner_addr"`          // <ip>:7777
}
type KnockResponse struct {
    KnockID         string `json:"knock_id"`              // 16 random bytes hex
    ReceiverX25519  string `json:"receiver_x25519_pub_b64"`
    ConfirmCode     string `json:"confirm_code"`          // "ABC-DEF" 20-bit
    TTLSeconds      int    `json:"ttl_seconds"`           // 300 default
}

// GET /clan/knock-list  — HMAC. Returns pending knocks for TUI display.
type KnockListResponse struct {
    Knocks []KnockEntry `json:"knocks"`
}
type KnockEntry struct {
    KnockID, JoinerMemberID, JoinerDisplay, JoinerAddr string
    JoinerIdentityFingerprint string  // first 8 hex of sha256(identity_pub)
    ConfirmCode               string
    ReceivedAt, ExpiresAt     time.Time
}

// POST /clan/knock-accept  — HMAC. Triggers the encrypted delivery.
// POST /clan/knock-deny    — HMAC. Marks knock denied; pings joiner.
type KnockDecisionRequest struct { KnockID string `json:"knock_id"`; Reason string `json:"reason,omitempty"` }

// POST /clan/knock-deliver — anonymous endpoint on the JOINER side.
// Authenticated by the AES-GCM tag, not by HMAC.
type KnockDeliverRequest struct {
    KnockID       string `json:"knock_id"`
    EncryptedBlob string `json:"encrypted_blob_b64"`  // AES-256-GCM ciphertext+tag
}
```

### Cryptographic core (`knock.go`)

Symmetric derivation on BOTH sides — receiver and joiner compute identical
`(key, nonce, confirmCode)` from the same inputs:

```go
shared := curve25519.X25519(myPriv, theirPub)         // 32 bytes
kdf := hkdf.New(sha256.New, shared,
                []byte("minti-knock-v1"),             // salt (static)
                concat(clanID, knockID, joinerPub, receiverPub))  // info
var bundle [32 + 4 + 12]byte                          // 48 bytes
io.ReadFull(kdf, bundle[:])
key, codeBytes, nonce := bundle[:32], bundle[32:36], bundle[36:]
confirmCode := fmt.Sprintf("%03d-%03d",
    binary.BigEndian.Uint32(codeBytes) % 1_000_000 / 1_000,
    binary.BigEndian.Uint32(codeBytes) % 1_000)
```

Receiver seals `WelcomeResponse-equivalent` plaintext:
```go
ct := aesgcm(key).Seal(nil, nonce, plaintext, []byte(knockID))  // aad=knockID
```
Joiner opens with the same key/nonce/aad. **The AES-GCM tag is the
receiver-authenticity proof** — no separate signature needed.

### KnockStore — mirror `InviteStore` pattern

```go
type KnockStore struct {
    mu      sync.Mutex
    pending map[string]*PendingKnock  // by knock_id
}
type PendingKnock struct {
    KnockID                                       string
    JoinerMemberID, JoinerDisplay, JoinerAddr     string
    JoinerIdentityPub, JoinerX25519Pub            []byte
    ReceiverX25519Priv, ReceiverX25519Pub         []byte  // discarded on consume
    ConfirmCode                                   string
    ReceivedAt, ExpiresAt                         time.Time
}

func (s *KnockStore) Consume(id string) (*PendingKnock, bool)  // CAS, first-wins
func (s *KnockStore) Sweep()                                   // TTL eviction, called from main.go ticker
```

Mirror `invite.go:78-91` exactly for `Consume` (delete-under-lock returning ok flag).

### Rate limits

Receiver-side:
- Per `JoinerAddr`: 10 knocks / 60s — reuse the sliding window from `peers.go:245-265` (`checkRateLimitLocked`).
- Per `clan_id`: 30 knocks / 60s — second bucket on the same `KnockStore` to stop a Clan-targeted swarm.

Joiner-side (`/clan/knock-deliver`):
- Per `knock_id`: hard cap of 1 successful consume (CAS); additional attempts 409.
- Per remote source IP: 5 attempts / 60s for unknown knock_ids (defense against attacker pre-seeding fake deliveries hoping to hit an honest joiner's pending knock).

## Threat model (document inline + in commit message)

| Attacker capability | Defence | Limit |
|---|---|---|
| Passive eavesdrop on LAN | TLS-with-SPKI-pin on /clan/knock leg; ECDH ephemeral keys → no long-term-key compromise | Standard |
| Active MITM substituting pubkeys | Confirm-code derived from BOTH pubkeys + `clan_id` + `knock_id` in HKDF info; operator visually verifies digits with joiner | Catches at ≈1/2²⁰ collision (≥500k MITM attempts per knock-window observable) |
| Replay of old `/clan/knock-deliver` | `knock_id` is single-use via CAS on joiner's KnockStore | After consume, knock_id rejected with 409 |
| Cross-Clan replay (attacker bridges two Clans) | `clan_id` in HKDF info; mismatched clan_ids → different keys → GCM tag fails | Hard cryptographic barrier |
| Spam knocks to DoS the Clan | Rate limits per joiner_addr (10/60s) AND per clan_id (30/60s) | Per `peers.go:245-265` pattern |
| Compromised existing member | Out of scope for M8; addressed by revocation (Phase C-rest + H-2 gossip) | v1 honesty |
| Brute-force the 6-digit code | 20-bit space + 5-min TTL + visual-verification step | Acceptable for human-eyeball flow; document explicitly |

## Deliberately NOT in M8 (scope-creep guard)

- **mDNS auto-discovery on joiner side** — paste-the-address only. The existing discovery package can power this in v1.5.
- **Multi-knock batch operations** — accept-all / deny-all from TUI. Per-knock decisions only.
- **Knock-via-Bluetooth/QR code** — out of scope; mDNS or paste address only.
- **Persistence of KnockStore across daemon restart** — in-memory only (mirrors InviteStore design). A daemon restart drops pending knocks; joiners time out and retry.
- **Rate-limit telemetry** — we'll audit-log each knock decision but won't surface "you got rate-limited" details in the TUI.
- **Identity rotation** — a joiner with a previously revoked Ed25519 identity will be visible to the operator via fingerprint; we don't auto-block them. Operator decides.
- **Cross-Clan knock forwarding** — joiner targets ONE Clan per knock command.
