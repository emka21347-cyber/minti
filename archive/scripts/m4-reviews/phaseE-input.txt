## 5. Leader-Lease Election

### 5.1 Why leader-lease, not pure gossip

Per peer-review (PRD v0.5), gossip-only election creates split-brain on partitions. The leader-lease model is "Raft-lite": real terms, real leases, real failover — without log replication (we have no state to replicate, only routing decisions).

### 5.2 Lease parameters

| Parameter | Value | Notes |
|---|---|---|
| `HEARTBEAT_INTERVAL` | 2s | Orchestrator emits a heartbeat this often. |
| `LEASE_DURATION` | 8s | Heartbeat carries `lease_until = now + LEASE_DURATION`. |
| `FAILOVER_GRACE` | 6s | If no heartbeat received for this long, peers begin election. |
| `ELECTION_TIMEOUT` | 1s | Time to wait for a new heartbeat before declaring election complete. |
| `MIN_TERM_INCREMENT` | 1 | Term must strictly increase on election. |

### 5.3 Heartbeat message

POST `/clan/heartbeat` to every peer every `HEARTBEAT_INTERVAL`:

```json
{
  "member_id": "<orchestrator>",
  "clan_id": "...",
  "term": 17,
  "lease_until": "2026-05-21T18:00:08Z",
  "reasoning_score": 72,
  "active_roster": ["uuid1", "uuid2", "uuid3"]
}
```

Peers update local state: `current_orchestrator = member_id`, `current_term = term`, `lease_expires = lease_until`.

A peer ignores a heartbeat if `term < current_term`, or if the sender is not the highest-`reasoning_score` member according to its current advertisements (anti-spoofing).

### 5.4 Election flow

When a member observes `lease_expires < now - FAILOVER_GRACE`:

1. **Candidate selection**: scan current advertisements for members where `capabilities.reasoning.enabled == true`. The candidate with the highest `reasoning_score` is the next Orchestrator. Ties broken by oldest `joined_at`. If a member has `pinned_orchestrator: true` and is reasoning-capable, it wins regardless.
2. **Term increment**: `new_term = current_term + 1`.
3. **Announce**: the candidate (or, if the candidate is *self*, this member) POSTs an "election announcement" heartbeat with `term = new_term` to all peers.
4. **Acceptance**: each peer accepts the first heartbeat for `new_term` from a candidate that matches its own scoring conclusion. If a peer's view disagrees (it scored a different member highest), it rejects with `409 Conflict, expected_orchestrator=<id>`.
5. **Settlement**: after `ELECTION_TIMEOUT`, if the candidate has received ≥ ⌈N/2⌉ accepts (where N = current active roster size), it commits the lease and begins normal heartbeat operation. Otherwise the election times out and is retried after a small random backoff (50–150 ms).

### 5.5 Split-brain handling

If two candidates simultaneously claim the same `new_term`:

- Peers see both heartbeats. Each peer accepts only the first received and rejects the second.
- The "loser" (whose accept count falls below quorum) yields, increments its `term` counter to match, and listens.
- If no candidate reaches quorum within `ELECTION_TIMEOUT`, both candidates abort, do a random backoff, and retry from step 1. The protocol terminates because backoffs eventually diverge.

### 5.6 User-pin override

A user may set `pinned_orchestrator: true` on their own member via Console or `cland pin`. While any reasoning-capable member is pinned:

- Pinned member wins all elections regardless of `reasoning_score`.
- If the pinned member becomes unreachable, the pin is auto-suspended until it returns (then resumed).
- Multiple simultaneous pins is a misconfiguration; v1 logs a warning and the lowest `member_id` wins.

### Phase E — Leader-lease election

- `cland/internal/election/` — heartbeat goroutine when lease-holder; election goroutine watching `lease_expires`.
- Parameters from spec §5.2 (HEARTBEAT_INTERVAL=2s, LEASE_DURATION=8s, FAILOVER_GRACE=6s, ELECTION_TIMEOUT=1s).
- **Quorum semantics under partition (spec §5.4 + §5.5 explicit):** `N` is computed from the **persisted active roster** (`clan.json`), not the live advertisement cache, so a partitioned 2/5 minority can't reach quorum (⌈5/2⌉=3). Both sides may still elect during partition; on heal the lower-`term` Orchestrator yields. This implements §5.5 verbatim.
- Candidate selection, anti-spoof, term tracking, **multi-pin tiebreaker (spec §5.6: lowest member_id wins, log warning)**.
- Tests: lone-member trivial election; two-member tied-score → oldest-`joined_at` wins; user-pin override; **multi-pin tiebreaker**; partition simulation (two locally-elected sub-Clans heal correctly); anti-spoof (refuse heartbeat from sender that isn't actually highest-score in receiver's view); random-backoff retry on split-brain.

# MINTI M4 Phase E — Leader-lease election

## Context

Phases 0/A/B/C/D of M4 are committed and validated. Two daemons can form a Clan, discover each other, and exchange capability advertisements; `peers.Registry` already tracks `LastSeenAt` + exposes `Live(now)` (4 s window) and `TouchLive(memberID)` waiting for a caller. **Phase E is what makes the Clan act like a Clan**: it elects an Orchestrator from the advertised candidates, keeps the lease alive with 2 s heartbeats, and re-elects within 6–8 s when the holder dies. Once Phase E lands, `peers.Registry.Live()` finally has the call site that gives it meaning (heartbeat receipt), and Phase F (routing) gains a real Orchestrator to route through.

This phase follows the **approved Phase E sub-plan in `velvet-drifting-codd.md`** (lines 242–248), refined for the Phase D code that actually shipped. Two scope choices confirmed by the user 2026-05-27:

- **Pin support is in scope** — `state.Clan.PinnedOrchestrator` + `minti-cland pin --self|--clear` CLI, so the multi-pin tiebreaker (M4 verification gate #16) is end-to-end testable now.
- **Both diagnostic endpoints ship** — `/clan/orchestrator` + `/clan/election/history`. Tiny, and the two-VM Phase J debug story needs them.

Spec authority: `docs/clan-protocol.md` §5 (v0.3). All cadence constants verified against the spec (HEARTBEAT=2s / LEASE=8s / FAILOVER=6s / TIMEOUT=1s / MIN_TERM_INCREMENT=1).

## Approach

### New package: `cland/internal/election/`

One package, three concerns split into files:

| File | Purpose |
|---|---|
| `state.go` | `State` struct holding `currentTerm`, `currentOrchestrator`, `leaseExpires`, `myLeaseExpires`. Mutex-guarded. Loads from + persists to `state.Clan` via `state.Store.SaveClan()`. Has `Apply(hb Heartbeat) error` for incoming heartbeats (returns reason on reject) and `Commit(term, winner, lease time.Time)` for own-election results. |
| `engine.go` | `Engine.Run(ctx)` — single goroutine driving both responsibilities: (a) if `state.Self == currentOrchestrator`, fan-out heartbeats every 2 s; (b) if `now > leaseExpires + FAILOVER_GRACE`, trigger an election cycle. Owns the ticker, the candidate-selection logic, the announce broadcast, and the ⌈N/2⌉ accept-counting. Uses `transport.Client` to POST heartbeats; uses `peers.Registry.Snapshot()` + `state.Clan.Roster` to compute candidates and quorum. |
| `handlers.go` | `/clan/heartbeat` (POST, HMAC), `/clan/orchestrator` (GET, HMAC), `/clan/election/history` (GET, HMAC). `historyRing` is a small in-memory ring of last 32 elections `{Term, Winner, Reason, At}` — not persisted; survives crash via re-election. |
| `engine_test.go` + `state_test.go` + `handlers_test.go` | Per the test matrix below. |

### Candidate selection — reuse, don't reimplement

Per spec §5.4:
1. Filter `peers.Registry.Snapshot().Members` to those with `LatestAd.Capabilities["reasoning"]["enabled"] == true` AND `Live(now)` (heartbeat-fresh) OR `AdFresh(now)` if no prior heartbeat exists (bootstrap).
2. Include `self` if local advertisement (synthesized in `engine.go` from the same `probe`/`scores` packages the advertise loop uses) is reasoning-capable.
3. **Pin path:** if any candidate has `pinned_orchestrator: true`, restrict the candidate set to pinned-only. If >1 pinned, lowest `member_id` (lexicographic) wins — log warning + audit entry per spec §5.6.
4. **Score path:** highest `reasoning_score` from `LatestAd.ReasoningScore`. Ties broken by oldest `AdmittedAt` — **the code calls `AdmittedAt` what the spec calls `joined_at`** (same semantic moment: admission into the current Clan). Add a one-line code comment at the tiebreaker site noting the spec alias.

### Quorum — persisted roster, not live ads

Per spec §5.5: `N = len(state.Clan.Roster where state == "active" || "admitted")`. Computed from `state.Clan`, not `peers.Registry`. Closes the partition gap (2/5 minority can't reach ⌈5/2⌉=3). Single helper `engine.quorum() int` returning `(N+1)/2`.

### State persistence

Extend `state.Clan` in `cland/internal/state/state.go`:

```go
CurrentOrchestrator string    `json:"current_orchestrator,omitempty"`
CurrentTerm         uint64    `json:"current_term,omitempty"`
LeaseExpires        time.Time `json:"lease_expires,omitempty"`
PinnedOrchestrator  bool      `json:"pinned_orchestrator,omitempty"` // self-pin
```

Persisted via the existing `Store.SaveClan()` atomic-rename path. Written on every heartbeat-applied + every election commit. Read at startup so a daemon restart preserves term continuity (avoids a same-term election clash with peers that didn't restart).

### Daemon wiring (`cmd/minti-cland/main.go`)

Right after the Phase D `advSvc.Start(advCtx)` line (~321), construct `election.Engine` with:

- `state.Store`, `id.MemberID`, `clan` snapshot, `peers.Registry`, `transport.Client` (reuse `advClient`), `crypto.KeyProvider`, `audit`, `log`, `config.Election`.
- A `localAdvertiser` adapter that yields the same advertisement payload `advSvc` builds (extract `advSvc.buildAdvertisement()` into a small reusable method on `advertise.Service` — currently inlined; rename only if needed).

### Heartbeat receiver → `peers.Registry.TouchLive`

The `/clan/heartbeat` handler calls `registry.TouchLive(hb.MemberID)` on every accepted heartbeat. That single line is the missing link Phase D left for Phase E and the thing that finally makes `peers.Member.Live(now)` true under normal operation.

### CLI: `minti-cland pin [--self|--clear]`

Add a `pin` subcommand under the existing dispatch in `main.go:54-87`. Posts to a new local-loop endpoint `POST /clan/pin {value: bool}` (HMAC-authenticated; same `localDaemonClient` pattern the other CLI subcommands use). The handler flips `state.Clan.PinnedOrchestrator`, `SaveClan`s, then bumps the advertise loop (`advSvc.Bump()`) so peers see the new pin on the next ad — pin propagates via the `Advertisement.PinnedOrchestrator` field that's already in `peers.Advertisement`.
